## 1. Purpose

This document records the long-term direction for WorldForge Studio as a **modular worldbuilding environment**, rather than only a map editor.

The application should let users create and maintain a coherent fictional world through specialized Studios that share one project and one consistent data foundation. Planned modules include Character Studio, Civilization Studio, History & Timeline Studio, Power System Studio and Story Studio.

This document also records a possible future companion product, **WorldForge Multiverse Conflict**, where users may bring worlds created in WorldForge Studio into asynchronous, multi-player conflicts with other users' worlds.

**Important:** This is a planning document. It does not change the currently approved implementation order. The active Asset System roadmap remains the source of truth for near-term development.

## 2. Product vision

### 2.1 WorldForge Studio

WorldForge Studio is intended to become a local-first, modular environment for creating, organizing, visualizing and maintaining fictional worlds.

A user should be able to work on multiple connected aspects of a world without maintaining disconnected documents or duplicating the same entities in different tools.

### 2.2 Product principles

1. **One world project, multiple Studios.** Map, characters, civilizations, powers and history belong to the same world project.
2. **Modular capabilities.** Each Studio owns a clear functional domain and can evolve without tightly coupling its implementation to other Studios.
3. **Shared identity and relationships.** A character, nation, city or organization should have a stable identity that can be referenced by other modules.
4. **Optional depth.** Users are not required to fill every data category. A world with only a map and a few nations remains valid.
5. **Local-first and portable.** Projects should remain usable locally and be exportable/importable through documented, versioned formats.
6. **Extensible schemas.** New modules and user-defined fields should not require breaking existing projects.
7. **Source data versus simulation data.** The user's authored world is distinct from changes generated by external simulations or multiplayer activities.

### 3.1 Application shell

The application shell should provide:
- Project Dashboard and project switching.
- Studio navigation.
- Shared search and entity navigation.
- Project settings and data validation.
- Import/export and backup.
- Consistent selection, notifications and command conventions where appropriate.

The shell should not contain the domain logic of every Studio.

### 3.2 World Data Core

World Data Core is the shared foundation for project identity, entity identity, relationships, schema/version management and persistence.

It should provide stable APIs/services to modules. It should not become a large collection of UI-specific code or a single monolithic business-logic file.

Responsibilities:
- World/project identity and metadata.
- Stable entity IDs and entity type registration.
- Cross-entity relationships and references.
- Schema versioning and migrations.
- Validation and integrity checks.
- Shared query/read services.
- Project persistence, archive and portable export contracts.
- Extension metadata for optional modules.

The Core should define contracts; domain-specific rules should remain in their owning modules.


## 3.4 WorldForge AI Layer and AI Gateway

AI is a shared optional capability across Studios, not a replacement for Studio workflows and not a mandatory runtime dependency. The application must remain fully usable with AI disabled.

Conceptual flow:

    STUDIOS / WORLD ASSISTANT
              |
       WORLDFORGE AI LAYER
              |
          AI GATEWAY
       /      |       \\
  Text Model Image Model Local Model
       \\      |       /
        MODEL ADAPTERS
              |
     STRUCTURED RESULT CONTRACTS
              |
      PREVIEW / VALIDATE / APPROVE
              |
        WORLD DATA CORE APIs

Responsibilities:
- Shared task orchestration and context assembly from World Data Core APIs.
- Provider/model adapters; provider routing by task; no hard dependency on one model.
- User-owned API key configuration or compatible local-model adapters; optional service-owned billing may be considered later but is not assumed.
- Usage/cost limits, retry/error handling, privacy controls and provider disclosure.
- Structured output contracts, validation, provenance and generation history.
- A permission-scoped tool/action interface for future agent workflows; no arbitrary code execution or unrestricted filesystem/data access.

Three levels of AI interaction are planned: Suggestion, Assisted Creation, and Agent. Agent operations must show a plan and proposed changes, validate them, request approval, then commit through normal Core services so History/Undo/Redo and auditability remain available.

AI-generated images entering Asset Studio must use the same import, normalization, metadata, license/provenance and Asset Pack validation pipeline as manually imported files. AI must not invent or certify distribution rights.

AI is a future architecture capability only. It does not change the active Asset System implementation sequence or authorize AI integration during the current Phase 3D–7 work.

### 3.3 Studio module boundaries

Each Studio should have:
- A defined domain and ownership of its data.
- A documented schema and validation rules.
- A service/API boundary.
- UI components independent of other Studio screens.
- Tests for its domain logic and integration contracts.
- A graceful behavior when optional related modules are absent or unused.

Modules should communicate through documented Core contracts or explicit integration services, not by importing arbitrary internal UI functions from one another.

## 4. Planned Studios and responsibilities

### 4.1 Map Studio — existing foundation

Primary domain:
- Map documents, layers and map objects.
- Geography and spatial representation.
- Continents, regions, territories and locations.
- Visual rendering and map export.

A map feature may reference a nation, city, organization or other world entity. The map is a spatial representation of world data, not the only place where that data exists.

### 4.2 Asset Studio — current priority

Asset capabilities remain a near-term priority under the existing roadmap.

Responsibilities:
- Asset Library.
- Asset Pack installation and lifecycle management.
- Asset Pack authoring, metadata editing and validation.
- .wfpack import/export.
- Reusable asset references and embedded project snapshots.

Asset Studio and Map Studio must share the same asset schemas, validator, registry and pack services. The current Phase 3D → Phase 4 → Phase 5 → Phase 6 → Phase 7 sequence is unchanged.

### 4.3 Character Studio

Proposed responsibilities:
- Character profiles and biographies.
- Appearance and personality.
- Attributes and custom fields.
- Character relationships.
- Family trees and lineage.
- Inventory/equipment references.
- Character affiliations and roles.
- Character-specific timelines and event participation.

Integration examples:
- Link a character to their birthplace and current location.
- Link a character to a nation, race, family, organization or faction.
- Link a character to abilities and power progression when Power System Studio is used.
- Link a character to historical events and story arcs.

Character Studio must remain useful even if Power System Studio is not used.

### 4.4 Civilization Studio

Proposed responsibilities:
- Nations, states and political entities.
- Races/species and populations.
- Cultures, languages and customs.
- Organizations, families, factions and institutions.
- Government and political structures.
- Economy, resources and military organization where the user chooses to model them.
- Relations, treaties and rivalries between entities.

A nation should be a structured entity that can reference territories and settlements on the map. The map geometry and the political/civilization record should remain distinct but linked.

### 4.5 History & Timeline Studio

Proposed responsibilities:
- Historical eras and periods.
- Events and event sequences.
- Causes, consequences and participants.
- Changes in territory, leadership, organization or population.
- Character, nation and organization timelines.
- Parallel timelines, alternate histories and branches.

Events should reference stable entity IDs rather than duplicating full character/nation records.

### 4.6 Power System Studio

Proposed responsibilities:
- Power sources and origins.
- Power types and systems.
- Levels, ranks, realms and sub-levels.
- Abilities, techniques and effects.
- Costs, limitations, prerequisites and side effects.
- Progression and evolution paths.
- Counters, synergies and interactions between systems.
- Custom rules and user-defined relationships.

Design constraints:
- Support linear, branching, nested and parallel progression structures.
- Do not force every power system into one universal rank ladder.
- Permit multiple systems (for example magic, cultivation, divine power, innate abilities and technology) to coexist.
- Keep rules configurable; do not hardcode one fictional world's metaphysics into Core.
- Link powers to characters, races, organizations, items, locations and historical events where relevant.

Power System Studio should be introduced after the shared entity foundation and the initial Character/Civilization capabilities are stable. It must not be a prerequisite for using WorldForge Studio.

### 4.7 Story Studio

Proposed responsibilities:
- Stories, series, arcs, chapters and scenes.
- Plot points and narrative branches.
- Character participation and development.
- Scene locations and time references.
- Links to historical events, organizations and power-system rules.
- Continuity checks against world data.

Story Studio should consume world data through shared references rather than maintain duplicate copies of characters, places or nations.

## 6. Shared data model principles

The exact schema should be designed and versioned during the World Data Core milestone. The following are design requirements, not a finalized JSON schema.

### 6.1 Stable identifiers

- Every world/project has a stable worldId.
- Every reusable entity has a stable entityId within a documented identity strategy.
- IDs must not depend on display names, UI position or map coordinates.
- Renaming an entity must not break references.
- Imported entities must preserve identity when they represent the same source entity, or receive new IDs with explicit provenance when they are copies.

### 6.2 Entity records and relationships

A conceptual entity record may contain:
- ID and entity type.
- Display name and aliases.
- Owning world/project.
- Schema version.
- Domain-specific data.
- Extension data.
- Provenance and timestamps where appropriate.

Relationships should be explicit records or typed references, with defined cardinality and validation. Examples include:
- Character → belongs to → Nation.
- Character → member of → Organization.
- City → located in → Territory.
- Nation → controls → Territory.
- Character → possesses → Ability.
- Event → involves → Character/Nation.
- Story Scene → occurs at → Location.

Do not assume all relationships are simple parent-child trees; many are many-to-many or time-dependent.

### 6.3 Optional modules and incomplete worlds

- Missing optional data must not make a project invalid.
- A world can begin with only maps and locations.
- Modules may provide default values or guided setup when a simulation requires data that the author has not supplied.
- Validation should distinguish errors from warnings and incomplete-but-usable data.

### 6.4 Schema versioning and extensions

- Every persisted project and portable package must identify its schema version.
- Migrations should be explicit, testable and preferably reversible through backups.
- Unknown optional extension fields should be preserved where safe, not silently discarded.
- Namespaces should prevent collisions between Core fields and module/plugin extensions.
- Avoid embedding module-specific business rules in the global project schema.

### 6.5 Source world data versus derived data

Keep authored source data distinct from derived or external activity data.

Examples:
- Authored source: a nation's canonical territory, a character's biography, a power system's rules.
- Derived/external: a battle result, temporary occupation, multiplayer damage, a simulation-generated event.

External systems must not silently overwrite canonical authored data. Any merge or synchronization should be explicit, reviewable and recoverable.

## 7. Future companion product: WorldForge Multiverse Conflict

This is a separate, optional product concept, not a Studio required for the initial WorldForge Studio release.

### 7.1 Product concept

Users create worlds in WorldForge Studio, publish or export a compatible world profile, and register those worlds in a shared multiplayer environment. Users can challenge, defend against or form alliances with other users' worlds.

The intended experience is an asynchronous, phase-based strategy and narrative simulation:
- A conflict is created between two or more registered worlds.
- Each phase presents context and available decisions.
- Players submit choices within a defined response window.
- A rules/result engine evaluates the choices against world profiles and current conflict state.
- Results update the conflict state and determine subsequent phases, events and choices.
- A chronicle records decisions and outcomes.

This is not intended initially as a real-time tactical game or a 3D battle simulator.

### 7.2 Conceptual service areas

- Account and ownership/authorization.
- World registration and import.
- World profile normalization.
- Challenge and conflict lifecycle.
- Phase and decision orchestration.
- Rules/result engine.
- Event generation and conflict state.
- Notifications and response deadlines.
- Audit log and war chronicle.
- Optional alliance and multi-world participation.

### 7.3 Data boundary and synchronization

- The registered world profile should be an explicit snapshot/version of the user's authored world.
- Conflict state belongs to Multiverse Conflict, not to the canonical WorldForge project.
- Opponents must not receive permission to edit another user's source project.
- A conflict result may be exported as proposed changes, events or a branch that the world owner can review and selectively import.
- Users should be able to choose whether their world is private, shared or eligible for challenges.
- Server-side validation, access control, rate limiting and tamper-resistant action logs are required for a public multiplayer service.

### 7.4 Cross-world compatibility and fairness

Worlds may use different genres and power systems (for example fantasy, science fiction, cultivation or magic). A future simulation ruleset must:
- Avoid relying on one universal power score as the sole determinant.
- Define scenario-specific conversion and resolution rules.
- Make rules visible before players commit to a conflict.
- Allow custom or community rulesets where appropriate.
- Handle missing data with transparent defaults or setup requirements.
- Provide a way to review outcomes and explain major contributing factors.

### 7.5 Suggested development stages

1. Private prototype: two imported world snapshots, manually configured rules and a small number of phases.
2. Two-player asynchronous conflicts: invitations, deadlines, decisions, result calculation and history.
3. Reusable phase/decision/rules templates.
4. Multi-world conflicts, alliances and factions.
5. Community discovery, moderation, reporting and scalable public services.

Do not begin this product until WorldForge Studio has a stable export/import contract and the World Data Core can provide reliable world profiles.

## 8. Non-goals and safeguards

- Do not turn the current Map Editor into a monolithic application that contains all future domain logic.
- Do not require every user to fill every Studio.
- Do not force a universal power hierarchy or a single genre.
- Do not allow external simulations to mutate a user's canonical world without consent.
- Do not make Multiverse Conflict a dependency of WorldForge Studio.
- Do not start all Studios in parallel before their shared data contracts are understood.
- Do not treat this planning document as evidence that any proposed module has been implemented.

## 9. Acceptance criteria for the architecture foundation

Before adding several Studios, the World Data Core milestone should demonstrate:

1. A project has a stable world identity and schema version.
2. At least two different entity types can be stored and retrieved independently of UI screens.
3. Entities can reference one another through validated stable IDs.
4. Renaming an entity does not break its relationships.
5. Project save/load preserves entity IDs, relationships and extension data.
6. Unknown optional module data is handled according to a documented compatibility policy.
7. A project without Character, Civilization, History or Power data remains valid.
8. Automated tests cover schema validation, migrations, references and persistence round trips.

Before Multiverse Conflict begins public testing, it should additionally demonstrate:
- Safe import of a versioned world snapshot.
- Strict separation of source world data and conflict state.
- Authorization checks for every player action.
- Deterministic/reproducible result evaluation for a fixed ruleset and input state, or a fully logged random seed where controlled randomness is used.
- An auditable record of choices, deadlines, rule versions and outcomes.
- Explicit owner approval for importing simulation results into the source project.
